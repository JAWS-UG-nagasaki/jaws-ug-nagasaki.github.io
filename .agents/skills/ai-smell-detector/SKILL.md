# JAWS-UG長崎 開催レポートの編集

`content/events` の開催レポートは、JAWS-UG長崎が「何を開催し、当日どんな学びと交流があったか」を記録し、次の参加につながる情報を残す公式記事である。個人の随筆や企業の広報文にはしない。

## まず集める情報

書き始める前に、依頼に含まれる情報を次の表に整理する。`content/events/_template.md` と既存の近いイベント記事を読み、frontmatter、見出し、リンク表記の慣例を引き継ぐ。

| 種別 | 必要な情報 |
| --- | --- |
| 開催事実 | 日時、会場、形式、主催、参加人数の内訳 |
| 当日の記録 | タイムテーブル、発表・ワークショップ・ゲーム、印象的な発言や出来事 |
| 裏付け | アンケート集計、写真、登壇資料、connpass、公式SNS投稿 |
| 次の案内 | 次回イベント名・日時・URL（確定している場合だけ） |

事実・参加者の感想・運営の解釈を混ぜない。人数、時刻、アンケート結果、固有名詞、引用、URLは提供された一次情報で確認する。情報がない場合は、もっともらしい描写や数字を補わず、該当段落を省くか「記録なし」と依頼者に確認する。

## 記事の組み立て

情報量に応じて、次の順で必要な節だけを使う。

1. 導入: イベント名、開催した事実、イベントの狙いを2〜4文で示す。
2. 開催概要: 日時・会場・形式・参加者数など、後から参照できる事実を箇条書きにする。
3. 当日の様子: 時系列やテーマごとに、実際に起きたことを具体的に記す。写真があれば、説明になる位置に置く。
4. 参加者の声・得られたこと: アンケートや発言を根拠に、引用と要約を区別して載せる。少数の感想を全参加者の総意にしない。
5. 運営メモ: 次回に活かす改善点や継続したい点を、責める語調にせず具体的に記す。公開に適さない内容は載せない。
6. 次回の案内・おわりに: 確定情報だけを案内し、参加者、登壇者、会場、協力者へ簡潔に感謝する。

すべての節を埋める必要はない。発表がなければ「発表内容」は作らず、アンケートがなければ「参加者の声」を推測で埋めない。

## 文体と視点

- 主語は「JAWS-UG長崎」「運営」「参加者」「登壇者」など、実際の主体を明示する。個人の体験談として書かない限り「私」は使わない。
- 基調は親しみのある丁寧語にする。内輪だけに通じる略語は初出で補足し、初参加者やAWS未経験者を置き去りにしない。
- 具体を優先する。「大盛況」「熱量の高い」「有意義な」「貴重な」といった評価だけでは終えず、参加人数、取り組み、発言、反応などで支える。
- 明るい出来事は率直に書くが、誇張・煽り・過剰な感謝の反復は避ける。未確認の成功談、参加者の心情、会場の評価を代弁しない。
- 改善点は、事実と次回の対応を組にする。個人の失敗や特定参加者が識別できる事情は、同意なく書かない。
- 一段落には一つの話題を置く。短い事実の文と、背景や意味を説明する文を混ぜ、定型的な同じ長さの段落を連ねない。

## AIらしさを除く編集

AIらしさは単語だけでなく、書き手が何を見て判断したかが見えないこと、同じ調子で要約を重ねること、文章の進行だけを説明することで生じる。公式レポートでは個人の毒や強い私見を足すのではなく、観測できる固有の出来事を中心にして直す。

### 主体・根拠・評価

1. **主体を名指す。** 「イベントでは説明が行われた」ではなく、「運営がルールを説明した」「登壇者が事例を紹介した」のように、行為者を明らかにする。会場、資料、アンケートなど、物に人間の動詞をさせない。
2. **事実・引用・解釈を分ける。** 人数や時刻は事実、かぎ括弧内は発言・回答、そこから得た意味は運営の解釈として書く。一つの文に混ぜない。
3. **総意を捏造しない。** 「参加者全員が」「多くの人が」「大盛況」は、集計や観察記録がある場合だけ使う。少数の感想は「アンケートでは〜という声があった」と範囲を示す。
4. **評価語を具体へ戻す。** 「有意義」「熱量が高い」「学びを深めた」「つながりを創出した」で止めず、何を試したか、どの話題が出たか、次回に何を変えるかを書く。具体に戻せない評価文は削る。
5. **強度を揃えない。** 良かったことは率直に書く。一方で未確認の成功談や参加者の内心を代弁しない。課題があれば、個人を責めず、事実と次回の対応を組にして記す。

### 段落・見出し・リズム

6. **見出しは内容を指す名詞句にする。** 「イベントは大成功でした」のような結論を見出しにしない。「ワークショップの様子」「参加者アンケート」「次回に向けた改善」のように、本文を探せる名前にする。
7. **一段落で一つの状況を更新する。** 実際の出来事、発言、数値、運営の判断のいずれかを前に進める。段落内で同じ事実を言い直さない。
8. **文の長さと役割に緩急をつける。** 短い事実で足場を置き、必要な背景を一文で補い、要点を短く締める。すべてを「〜しました。〜しました。〜しました。」にも、すべてを長い説明文にも寄せない。
9. **具体と意味づけを往復する。** 写真、時刻、カード、発表テーマ、発言などに寄る段落の後で、その出来事が次回にどうつながるかを一段だけ引いて書く。抽象的な段落を連続させない。
10. **並列は情報量に応じて使う。** タイムテーブル、登壇一覧、アンケート結果には箇条書きや表を使う。本文で「A、B、C」と三つ並べるだけの要約は、最も重要な一つを文で説明するか、必要な二つに絞る。

### 進行実況を消す

11. **文書ではなく当日を話題にする。** 「ここから当日の様子を紹介します」「最後に振り返ります」「次は参加者の声です」は削る。見出しと本文の内容で読者を進める。
12. **書き方の説明を本文に漏らさない。** 「具体例を挙げると」「このことから分かるように」「重要なのは」のような接続だけの文は、前後の事実が成立しているか確かめ、不要なら削る。
13. **例外は読者の理解に必要な案内だけにする。** 写真の説明、引用の出典、注意事項、未確定情報の断りは残す。これらは文書の進行ではなく、公開情報の正確さを支える。

### 語彙・記号・定型

14. **反復する定型を具体化する。** 「本イベントでは〜を開催しました」「〜を通じて学びを深めました」「参加者同士で活発な交流が行われました」「今後も場づくりを継続します」を機械的に繰り返さない。
15. **抽象語を一記事に撒かない。** 「コミュニティの活性化」「価値ある場」「つながり」「熱量」「手応え」「学び」「成長」「本質」などは、根拠のある一度の使用にとどめる。言い換えられなければ削る。
16. **借り物の比喩を避ける。** 「思考のOS」「インストール」「ハック」「アップデート」などは平易な日本語に戻す。AWSの正式名称や技術用語は、意味を変えないために必要なら残す。
17. **記号を掃除する。** 全角ダッシュ、装飾目的の絵文字、不要な太字、形容詞を囲むかぎ括弧を取り除く。中黒の過剰な並列は「と」「や」または箇条書きに直す。かぎ括弧は固有名詞、引用、誤読を避ける語だけに使う。
18. **対比を作りすぎない。** 「AではなくB」「初心者から上級者まで」「技術だけでなく交流も」を連発しない。本当に対比が必要な一度だけにし、その他は当日あった出来事をそのまま書く。

### 編集の優先順位

1. 事実誤認、引用・画像・個人情報の公開範囲を直す。
2. 主体のない文、根拠のない総括、参加者の心情の代弁を直す。
3. 進行実況、重複、抽象語だけの段落を削るか具体へ戻す。
4. 見出し、段落の話題、文の長さを調整する。
5. 偏愛語、借り物の比喩、記号、表記揺れを整える。

## 公開前チェック

- [ ] frontmatterのTitle、Date、Category、Tags、Slug、Connpass、Summary、Imageを既存記事の形式に合わせた。
- [ ] 日時、会場、参加人数、登壇者名、URL、引用文を一次情報と照合した。
- [ ] 事実、引用、運営の解釈が読み分けられる。
- [ ] 実際に起きた出来事があり、抽象的な称賛や定型の総括だけで終わっていない。
- [ ] 個人情報、顔写真、SNS投稿、社名・発言の掲載に必要な同意・公開範囲を確認した。
- [ ] 次回の案内は確定済みで、リンク先を確認した。未確定なら削除した。
- [ ] 文末、見出し、記号、リンクの表記が既存記事と整合している。
- [ ] 主体のない受け身、物を主語にした人間的な動詞、根拠のない「多くの人」「大盛況」を残していない。
- [ ] 各段落は出来事・発言・数値・運営判断のいずれかを前に進め、進行実況や同じ内容の言い直しを含まない。
- [ ] 定型の称賛、三項並列、対比、抽象語、記号が連続していない。

## 仕上げ方

執筆依頼では、本文だけでなく「使った事実」「情報不足で省いた節」「確認が必要な箇所」を短く添える。編集・レビュー依頼では、事実誤認や公開上の懸念を最優先に指摘し、次に重複・抽象語・定型表現を直す。
